# Workflow Examples

Representative agent workflow patterns, sanitized. These are illustrative — actual production workflows live in private repositories.

---

## Pattern 1: Research → Proposal → Human Review

**Goal:** an agent investigates a question, writes up findings, and proposes a concrete change. A human approves before anything ships.

```
1. Operator opens a task with a clear spec:
   - "Update the README to reflect the new architecture diagram."

2. Agent gathers evidence:
   - Reads the current README.
   - Reads the architecture doc.
   - Diffs the two, identifies inconsistencies.

3. Agent assembles a proof bundle:
   - Files read.
   - Specific lines flagged.
   - Proposed change as a diff.

4. Agent opens a pull request:
   - Branch name encodes the task ID.
   - PR description includes the rationale and the proof bundle reference.

5. Human reviews the diff in GitHub, merges or requests changes.

6. Task coordinator records the outcome and the rubric score.
```

What this avoids: agents writing directly to the main branch, agents producing changes without a paper trail.

## Pattern 2: Committee Analysis with Policy Gate

**Goal:** several agent instances analyze the same input independently, then a policy layer decides whether to act on the majority verdict.

```
1. A request enters the gateway.

2. Three agent instances (potentially different providers) run the analysis
   in parallel against the same input.

3. Each returns a structured verdict:
   { "verdict": "...", "confidence": 0.0..1.0, "reasoning": "..." }

4. A small aggregator service compares verdicts:
   - All three agree, high confidence → routed to "allow."
   - Mixed verdicts or low confidence → routed to "require approval."
   - Unanimous "deny" → routed to "reject with reason."

5. The policy layer applies the routing decision.

6. The entire committee transcript is logged for later evaluation.
```

What this avoids: relying on a single model's output for high-stakes decisions, losing the disagreement signal that single-model setups discard.

## Pattern 3: Paper-Only Research Cockpit

**Goal:** model a real-world reasoning task end-to-end, but never execute any irreversible action. Used in the paper-trading research project.

```
1. A research question is loaded as a task.

2. Multiple agents propose analyses:
   - A "bull" agent argues one direction.
   - A "bear" agent argues the other.
   - A "risk" agent flags downside scenarios.

3. A judging agent summarizes the three views and produces a structured
   recommendation with explicit confidence.

4. The recommendation is logged as a paper outcome with a timestamp.

5. **No live execution happens.** No broker is called. No order is placed.
   The system is research-only.

6. Outcomes are scored later against ground truth (what actually happened)
   to build an evaluation history.
```

What this avoids: any path where an LLM's recommendation could result in a real-money trade. The cockpit is explicitly a research surface, not a trading system.

## Pattern 4: Missed-Communication Recovery

**Goal:** when a real-world event implies a follow-up is needed (e.g., a missed phone call to a small business), generate a context-aware response and queue it for the operator's review.

```
1. Event arrives:
   - A signal indicating a missed inbound contact, with context (caller ID,
     time of day, prior interaction history if available).

2. Agent drafts a response:
   - Reads recent customer-facing copy to match tone.
   - Generates a short message tuned to the context.

3. Response goes into a review queue, not an outbound channel:
   - The operator sees the draft.
   - The operator edits or approves.
   - Only after approval does the message send.

4. After send, the system schedules a follow-up reminder if no reply
   arrives within a configured window.
```

What this avoids: outbound communications generated by an agent reaching customers without human review.

---

## Common Threads

Across all four patterns:

- **Tasks are explicit.** Each has an ID, a spec, a state, and an outcome.
- **Side effects go through gates.** Writes, sends, and merges require explicit approval or policy clearance.
- **Evidence is bundled.** What the agent read, what it concluded, and why — all attached to the task.
- **Logs are first-class.** Not an afterthought, not optional.
- **Reversibility is the default.** Drafts not sends. Branches not main. Paper not live.
